- **Task Checklist's bulk-delete select-all checkbox never showed an indeterminate state — a straight porting gap, not a design choice.** `old-portal/js/tasks.js:1020`'s `tOnCheckChange()` sets `all.indeterminate = _tSelectedIds.size > 0 && _tSelectedIds.size < total` (scoped to the current page's rendered rows, via `document.querySelectorAll('.t-row-cb').length`), but the original React port of `TaskTable.jsx` only ever computed `allChecked` and never carried the indeterminate visual over. Found and fixed while migrating this table onto the shared table system (`src/components/shared/table/`)'s `CheckboxTh`, which supports an `indeterminate` prop directly: `TaskTable.jsx` now derives it the same way production does — some-but-not-all of the current page's rows selected — via `rows.some(r => selectedIds.has(r.id)) && !allChecked`.

## Known confusing-but-intentional-looking access boundaries
Distinct from both "Dead code observed" (unreachable code) and "Bug fixes made" (plain bugs with no downside to fixing) — these are real access-control boundaries in production today that read as accidental but touch who can actually perform an action, not just cosmetics. Deliberately **ported exactly, not fixed**, per an explicit decision: changing either would silently expand who can act on certain FMS orders, which is a business/security call for the team to make deliberately via Access Control, not something to change as a side effect of migration. Flagging both here for the team to review separately if they want to actually change them.
- **FMS's `fms_config` permission flag currently has no effect unless the grantee is already one of the 5 hardcoded config-team emails.** The Config action button's gate (`old-portal/js/fms.js`'s `fmsRenderTable`) is `isConfig && FMS_CONFIG_EMAILS.includes(email)`, where `isConfig = fms_config==='true' || FMS_CONFIG_EMAILS.includes(email)`. By boolean algebra, `(A || B) && B` always equals `B` — so granting `fms_config` to a 6th person who isn't already hardcoded does nothing to the button's visibility, even though Access Control's UI still presents it as a real, independently-grantable toggle (`fms_config: '⚙️ FMS Config (Device Configuration)'` in `PERM_LABELS`). Ported as `canActOnConfigStage` in `lib/fms.js`, with the exact same redundant `&&`.
- **Certification access doesn't follow the "send to Anish" routing.** The pure-cert-to-Anish bypass never updates `assigned_to_support`, and the Certify button is gated identically to the plain Assign button (`isSupport && myEmail === assigned_to_support || override`) — not by config-team membership. So after routing a cert order "to Anish," the table's Certify button only actually works for whoever the order was *originally* assigned to, or an override user — Anish himself needs `fms_override` (likely already granted to the config team in practice) to act on it, not the routing itself. Ported as-is in `FMSPipelineTable.jsx`'s `resolveAction`.
- **CRM Vehicle's `can_view_crm` tier-lock branch is real code with no way to trigger it through any built admin UI.** `_getCRMAccessLevel()` (`old-portal/js/crm.js`) returns a literal tier name (e.g. `'Platinum'`) when a non-super-admin's `can_view_crm` permission is set to a tier string instead of `'true'`/`'false'` — this locks their whole view to that tier (server buttons hidden per their `crm_server_*` toggles, tier buttons disabled via `pointerEvents:none`). But `js/adminperms.js` (ported byte-for-byte into our Access Control panel) renders `can_view_crm` as a plain boolean toggle, same as every other permission except `checklist_scope`'s special-cased select — there is no UI, old-portal or ours, that can actually write a tier-name string into this permission. It only ever takes effect if someone hand-edits the row directly in the database. Ported as a real, working code path in `lib/crmVehicle.js`'s `getCrmAccessLevel()` — team should decide whether to wire up a way to set it in Access Control, or remove the branch as truly dead.
- **CRM Vehicle's server-scoping is inconsistent between the main table and Vehicle Changes.** The main customer table only filters by the viewer's allowed servers (`crm_server_premium/pro/goa/bangalore/gujarat`) when their access level is `'restricted'` — a tier-locked viewer's "both servers" query pulls **all** servers' data for their tier with no server filter at all, even though their server-switch buttons are hidden per those same toggles. Meanwhile the Vehicle Changes fetch applies the allowed-servers filter regardless of access-level type. So a tier-locked, single-server-permitted viewer sees cross-server data in the main table but single-server-only data in Vehicle Changes for the same login. Ported as-is — both branches kept exactly as separate as production keeps them.
- **CRM Vehicle's Customer Alerts banner and Acknowledge action have no access scoping at all.** `loadCustomerAlerts()`/`crmAcknowledgeAlert()` (`old-portal/js/crm.js`) fetch and PATCH `customer_alerts` with zero tier/server filter — every viewer who can open the panel at all (any access level except `'none'`) sees and can acknowledge every Platinum vehicle-count-drop alert company-wide, regardless of their own tier-lock or server-restriction. Ported as-is in `lib/crmVehicle.js`'s `fetchCustomerAlerts`/`acknowledgeCustomerAlert` — no viewer-scoping added.
- **CRM Vehicle's KPI delta arrows use a denominator that doesn't match the tiles they sit next to.** The Active/Running/Idle/Stop/Inactive delta arrows are always computed from `daily_fleet_stats`' whole-fleet snapshots (`tier=eq.All`), never filtered by the viewer's own tier — so a tier-locked viewer's KPI *values* are correctly scoped to their tier, but the delta *percentages* next to them are computed against total-fleet history, not their own tier's history. Ported as-is in `crmLoadKpiDeltas`.
- **CRM Vehicle's "Total Vehicles" delta ignores the active tier filter, unlike the Added/Removed summary cards right next to it.** `crmLoadKpiDeltas`'s `fetchCount` (used for the Total Vehicles ▲/▼ net-change arrow) queries `vehicle_changes` with no `tier` clause at all, while `crmChgLoad`'s `fetchChanges` (used for the Vehicles Added/Removed summary cards and the company-breakdown detail panel) does apply `&tier=eq.${_crmTier}` when a tier filter is active. So with e.g. Platinum selected, the Added/Removed cards correctly show only Platinum changes, but the Total Vehicles delta arrow reflects the net change across all tiers — two visually-adjacent numbers computed over different scopes. Found while writing `lib/crmVehicle.js`, not during the original investigation pass. Ported as-is: the tier clause is present in `fetchVehicleChanges` (used by both the summary cards and detail panel) and deliberately absent from the total-vehicles net-count query.
- **Customer Mapping's clear-mapping (✕) button is gated on the wrong field, leaving some genuinely-mapped rows impossible to unmap through the UI.** `mpRenderTable()`'s odoo cell (`old-portal/js/mapping.js`) only renders the ✕ icon when `r.canonical_name` is truthy — but live production data (confirmed via the actual `/api/mapping-data` response during investigation, not just code-reading) contains rows where `is_mapped: true` and `customer_id` is a real, non-null id while `canonical_name` is an empty string. For these rows the clear icon simply never renders, even though the row is genuinely mapped — there is no way to unmap it through the UI at all (short of re-mapping it to something else first). Confirmed and approved before building: ported byte-for-byte in `MappingOdooCell.jsx` (gated on the same `row.canonical_name` field, not `row.customer_id`, which would actually catch these rows) rather than silently fixed, since changing the gate would change who can clear which mappings — a call for the team to make deliberately, same category as the FMS/CRM Vehicle entries above.
